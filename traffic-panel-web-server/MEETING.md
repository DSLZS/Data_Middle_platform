# 会议纪要

## 一、系统框架与功能模块讨论

- **系统主页**：设计为"全域事态看板"，采用大屏形式展示，包含各类指标和热力图等，类似于数字孪生大屏。
- **收纳栏目**：另设两个收纳栏目，用于承载具体业务内容。
- **初步确定的业务方向**：
  - 利用1月3日至7日的数据进行早晚高峰上下车点分析，生成公交线路建议。
  - 884区间分析报告。
  - 夜间经济活力分析（如晚9点至凌晨2点的热力图），需先确认数据是否支持小时粒度。

## 二、技术选型与数据依赖

- **数据库选型**：倾向于使用 PostgreSQL (PG)，放弃 MySQL。Hala 将负责在本周内完成数据迁移。
- **GPS数据需求**：杨溪需要部分原始GPS数据（如 `trips` 表中的经纬度数组或 `gps_point` 表中的单条记录）进行轨迹回放功能的开发和测试。数据频率可能较高（如10Hz），可考虑在后端或数据层进行抽稀处理。
- **数据获取路径**：依赖锐鸿提供原始数据示例，或等待 Hala 完成数据迁移和数仓加工后提供。

## 三、开发分工与优先级

- **大屏展示**：相对简单，已有5个看板可由崔哥的前台直接调用报表数据接口展示。
- **开发负责人**：杨溪和崔哥负责前后端开发。
- **开发优先级**：
  - **优先**：先完成大屏和空间决策规划等简单模块，确保先有产出。
  - **后续**：轨迹回放、违规驻留分析、重点交通枢纽接驳效率等较复杂功能后续视情况开发。

## 四、数据与业务匹配性

- **数据局限性**：认识到仅凭5天的数据分析存在局限性，但可作为演示基础。
- **地图匹配问题**：对于轨迹回放等可能因数据年份（2015年）与当前地图不匹配导致点位偏差的问题，计划通过筛选部分与现状匹配良好的路线进行演示，并解释为数据清洗/降噪结果。
- **总体评估**：现有数据足以支撑项目内容，具体故事阐述可在功能实现后进一步细化。
